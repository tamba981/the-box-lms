### Feature detail — course cover images (`5b36c44`)

- Stored as a Buffer in MongoDB, **not** on disk — the container filesystem is discarded on every deploy.
- Client downscales on canvas to max 1280×720 JPEG before upload. Measured: 136 KB PNG → **18.5 KB** uploaded.
- Server validates on **magic bytes**, not the client-supplied data-URL prefix (that is not evidence).
- 600 KB cap; `THUMBNAIL_BAD_TYPE` / `THUMBNAIL_TOO_LARGE` errors.
- 14 dedicated API tests, all passing.

## 2. Defects found and fixed

These were found by measuring, not by looking. They are the kind of bug that survives review.

### 2.1 One grey, wrong on both themes

`--text-light: #6b7280` was doing double duty and failing on **both** backgrounds:

| Background | Measured | Required |
|---|---|---|
| Light theme page background `#f4f6f9` | **4.47:1** | 4.5:1 |
| Dark theme background | **3.65:1** | 4.5:1 |

It had only ever been checked against pure white, but the pages paint `#f4f6f9`. **Every page
on the site** had marginally unreadable secondary text in light mode and badly unreadable text
in dark. Now `#656e7c` light / `#94a3b8` dark.

### 2.2 CSS specificity turned every course title blue

`body.dark-mode a` has specificity (0,1,2) and **out-ranks** the course card's own
`color: inherit` (0,1,0). On the dark theme, every course title and price in the catalog
rendered in link blue at 3.98:1. Light mode was fine, which is exactly why it hid.

### 2.3 An inline style that could not follow the theme

The "Preview" tag on the syllabus used `style="color:var(--primary)"` — inline styles beat
every stylesheet rule, so it stayed at 2.37:1 on dark. Now a class.

### 2.4 The mobile menu was invisible in dark mode

Nav links kept the light-theme text colour on a panel that goes dark: **1.22:1**. On a phone,
in dark mode, the navigation was effectively not there.

### 2.5 Fabricated data removed from the served HTML

The homepage shipped six hardcoded category cards with invented counts — *"Business &
Management / 124 Courses"*, *"98 Courses"*, *"76"*, *"63"*, *"58"*, *"45"*. These were
replaced by JavaScript on load, but were visible whenever that fetch failed, and they
contradicted the real catalogue (5 courses). Removed.

> **Standing rule:** this project does not put invented numbers in the UI. Every figure comes
> from the API or shows `—`. This has been a recurring defect — check any mock data before it
> reaches a page.

### 2.6 Case-only folder mismatch

Renaming `Imges` → `Images` broke 25 references while **every page kept working locally**,
because Windows resolves either case. On the case-sensitive Linux container it would have
404'd the logo on every page at once, after deploy. The build gate (`scripts/check.js` §7) now
resolves every referenced asset by case-sensitive comparison.

## 3. Verification

- **`npm run verify` → 190/190 checks passing.** One suite earlier reported 184 — that was two
  suites silently *skipping*, not the product being healthier. The count is printed deliberately.
- **Contrast, measured in the browser after the fix, both themes, 0 failures:**
  `/index.html` · `/courses.html` · `/course.html` · `/certificate.html` · `/terms.html` ·
  `/privacy.html` · `/forgot-password.html` · `/verify-email.html` · `/404` ·
  `/instructor-dashboard.html`
  The only remaining hit is the *disabled* submit button, which WCAG 1.4.3 explicitly exempts.
- **Build gate:** 85 files parsed, 323 imports resolved, 67 local assets resolved, 10 dependencies present.

**Methodology note.** A scripted walk of every text node — compositing the real ancestor
background stack and computing the WCAG ratio — found all of the above. Page-by-page visual
checking found none of it. Two traps if you repeat it:

1. `background-color` is transparent under a gradient or image, so the walk falls through to
   `body` and reports nonsense. Skip those elements.
2. `body` has a `0.3s` background transition, so read after ~700 ms or you measure the new text
   colour against the old, mid-animation background.

   was committed in `054c489`. It was never an ancestor of `main` and never pushed; the local
   branch holding it has been deleted. Treat the values as compromised regardless.

   (`.env.*`, which re-admits only `.env.example`) and has been deleted from the working copy.

`frontend/public/Images/hero/hero.mp4` and untracked. Video and markup land together, in one
change, once compressed.

## 6. Railway variables

Derived from what the code actually reads (`backend/src/config/env.js` and its callers), not
from a template.

| Variable | Value | Notes |
|---|---|---|
| `NODE_ENV` | `production` | Enables the production secret-length checks |
| `MONGODB_URI` | Atlas connection string | See the warning below about the database name |
| `JWT_ACCESS_SECRET` | new value | Copy from `backend/.env`. Must differ from the refresh secret, ≥32 chars |
| `JWT_REFRESH_SECRET` | new value | Copy from `backend/.env` |
| `PUBLIC_BASE_URL` | `https://the-box-lms-production.up.railway.app` | The Railway host until the custom domain exists. **No trailing slash.** It is the link inside verification and reset emails, and the address payments redirect to |
| `CORS_ORIGINS` | *(empty)* | May legitimately be empty — same-origin is inferred. Set only if a different origin must call the API |
| `PORT` | let Railway set it | The app reads it; Railway injects it |
| `LOG_LEVEL` | `info` | |
| `RESEND_API_KEY` | required for email | Verification and reset emails cannot be delivered without it |
| `EMAIL_FROM` | address on a Resend-verified domain | Resend refuses to send from an unverified domain |
| `STRIPE_SECRET_KEY` / `STRIPE_WEBHOOK_SECRET` | optional | Stripe cannot serve a Liberian business — see `docs/PAYMENTS.md` |
| `ORANGE_MONEY_*` / `LONESTAR_MOMO_*` | optional | Setting these makes the methods *selectable*, not *payable*; charge calls are deliberate stubs |

`FRONTEND_URL` **does not exist in this codebase** — nothing reads it. Do not add it.
`SEED_PASSWORD` is read only by the seed script and is not needed in production.

**Warning on `MONGODB_URI`.** The seed tooling and `npm run new-secrets` both recommend a
separate production database. Production currently pointing at `wuteve_dev` means real student
accounts share the database this machine runs its test fixtures against. The smoke suite
creates `smoke-*` fixtures and tears them down, but a mistake there writes into live data.
A separate `wuteve` database is the safer arrangement, and costs one extra Atlas database.
